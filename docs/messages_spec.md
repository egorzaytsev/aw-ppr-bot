# Пепе: переработка всех сообщений бота — задание

Основа: `docs/messages_inventory.md` (опись от 08.11.2026, коммит 0648c22). ID сообщений — оттуда.
Все решения ниже согласованы с Егором 08.11.2026. Делать всё по этому документу; где документ молчит — применять общие правила из раздела 1.

---

## 1. Общие правила (для каждого из 202 сообщений и 44 вопросов анкеты)

1. **Смысл с первого прочтения.** Каждое сообщение отвечает на два вопроса: что случилось и что теперь делать. Если делать ничего не нужно — так и написать («Делать ничего не нужно»).
2. **Без техники.** Ни одного английского имени поля или значения Airtable (Target Project, Reg Status, Decision, Need more info, PPR Next Step Missing, People, Inbox, Projects, Simplified/Full, Accept — merge и т.д.), ни chat_id, ни rec…/tbl…, ни текстов исключений. Люди — по имени, проекты — `Название Референс`, компании — по названию. Если имени нет — «неизвестный пользователь», не ID.
3. **Значение формулы PPR Next Step Missing** везде выводить через русский словарь (как в NEXT_STEP_RU / ASK_RU). Неизвестный ключ — не выводить сырым, а писать в лог и показывать «другие данные».
4. **Любой текст дилеру от имени Егора/Лолы проверяющий видит до отправки** — полным текстом, с кнопками «Отправить» / «Изменить текст» / «Отмена». Касается: готового запроса недостающего (ADM-29, ADM-06), автокомментария «Принято как предрегистрация…» (ADM-36), рассылки о чужой предрегистрации (DLR-37 — см. решение 13).
5. **Карточка-вопрос проверяющему** всегда содержит четыре части:
   1) что пришло — само содержание (текст, номер квотации, имена файлов, расшифровка голосового);
   2) что изменится в базе при «Принять» («запишу квотацию в проект, статус не меняется» / «проект перейдёт в регистрацию» / «создам новый проект»);
   3) что получит дилер — полный текст;
   4) кнопки с понятным результатом.
   Пустая заявка (дилер ничего не прислал) проверяющему не уходит вовсе; дилеру — DLR-24.
6. **Выход есть всегда.** Каждый запрос ввода (у проверяющего и у дилера) — с кнопкой «Отмена». Каждый обязательный вопрос анкеты — с кнопкой выхода. Нет сообщений, отсылающих к кнопке, которой нет.
7. **Тупиков нет.** После каждого сообщения ясно, кто делает следующий шаг. Сообщения без следующего шага и без ценности — убрать.
8. **Маршрут.** Дилерам, чьи заявки идут Лоле, бот пишет «Лола», а не «Егор» (DLR-22, DLR-27, SYS-12, PHR-05, DLR-38 и все «Егор подтвердит / передал Егору»). Имя проверяющего берётся из маршрута, не по умолчанию.
9. **Ошибки.** Проверяющему не присылать ошибки, которые бот пережил сам (тайм-аут с успешным повтором, пауза сбора). Оставшиеся — по-русски: что случилось, кого касается (имя, проект), что сделать. Технические подробности — только в логах Railway. В сводке 9:00 — счётчик пережитых сбоев одной строкой.
10. **Язык.** Падежи и род (ADM-38 «подтверждаю предрегистрацию», ADM-42 «напиши Егору», SYS-09 «как предрегистрацию», CMD-07 и DLR-03 без рода читателя, REM-04 «21 дня»). Даты — `дд.мм.гггг`, не ISO. Одно понятие — одна формулировка: «плейсмент», кнопка «Дополнить материалы» (не «Дополнить»), «Мои проекты». Фразы-реакции (PHR-01) не ставить после «Пропустить». Убрать повтор «передал Егору» (PHR-05 vs done_text).
11. **Обращения к дилеру не попадают проверяющему.** В копии «Взято в работу» (ADMM-11, CRD-13) и в сводке проекта (ADM-08) убрать «Твой номер…», «👉 Всё это можно добавить…» — писать в третьем лице («номер дилера в предрегистрации — второй из трёх»).
12. **Длинные сообщения** (SYS-13, CMD-16, ADM-13, ADM-08 с журналом) — через то же разбиение, что send_card; журнал проекта — последние 5 записей, не целиком.
13. **Состояние ожиданий** (откат ADM-23, звонок ADM-16, пошаговая проверка SYS-04, ready_offered, calls_confirmed) хранить так же, как остальные ожидания (Bot Processed / Airtable), а не только в памяти.

## 2. Решения Егора по логике

**Р1. «Пока оставить» при повышении (ADM-02, SYS-08, ADM-01).** Дилеру сообщать. После «Пока оставить» — запрос причины (с «Отправить без комментария» и «Отмена»), дилеру: «По проекту {Название Реф} статус пока остаётся «{текущий}».[ Комментарий: …] Когда появятся новые данные — «Обновить проект» → «Дополнить материалы»».

**Р2. Кнопка «Отказать» на шагах повышения (ADM-01/02, SYS-04, SYS-08).** Добавить «❌ Отказать» → причина или «Отправить без комментария» → дилеру отказ в повышении (как DLR-31, текущий статус сохраняется — исправить CRD-08: не писать «зафиксирован как уведомление», если у дилера уже предрегистрация).

**Р3–Р4. Комментарий после решения.** Третьей кнопки на карточке не добавлять. После «Принять» и после «Отклонить» всегда: «Напиши комментарий дилеру» + кнопки «Отправить без комментария» / «Отмена» (уже так — сохранить везде, включая Р1, Р2, откат). Отказ без комментария допустим, но дилер получает не «отказ», а: «Заявка по проекту {Название Реф} не принята.» + что можно сделать дальше («Если появятся новые данные — подай заново через «Новый проект»» / для обновлений — «…через «Обновить проект»»). DLR-35 — добавить project_line.

**Р5. Застрявшие решения — кнопками в боте, не через Airtable (ADMM-09, ADMM-10, ADMM-05, ADMM-06, ADM-26/27).**
- Не указан проект → кнопки «В проект: {похожие}» / «Создать новый проект» (как ADM-34).
- Неясно, какой статус → кнопки «Уведомление» / «Предрегистрация» / «Регистрация».
- Не хватает данных → карточка по правилу 1.5 с готовым запросом дилеру и кнопками «Отправить запрос» / «Изменить текст» / «Принять как {этап ниже}» / «Отмена».
- Регистрация уже у другого / предрегистраций больше трёх → «Принять как уведомление» / «Отклонить».
- Нет автора заявки → по-русски, кого не хватает, кнопка «Отклонить заявку».
Текст: «Решение по «{проект}» не прошло: {причина по-русски}. Выбери:» + кнопки. Значения Decision выводить по-русски («принята», «принята в проект», «отклонена»).

**Р6. Выигран / проигран (DLR-32, CRD-09, сценарии WON/LOST).** При «Принять» записывать в проект: выигран → Status = Won, Probability = 100, номер заказа/проформы (если прислан) в Quotation / Proforma и Project Log; проигран → Status = Lost, Probability = 0, причина в Project Log. Дилеру: «Записали: проект {Название Реф} выигран. Спасибо!» / «Записали: проект {…} проигран, причина — {…}.» Без «подтвердит Егор». Проверяющему в карточке-вопросе (п. 1.5) показать, что изменится.

**Р7. Звонок, другое время (ADM-42).** Дилеру — кнопки «✅ Подходит» / «🕑 Предложить другое». «Подходит» → проверяющему «{Имя} подтвердил звонок {время}», звонок считается подтверждённым. «Предложить другое» → дилер пишет время → проверяющему с кнопками «Подтвердить» / «Другое время». Добавить у проверяющего в ADM-10 кнопку «Звонок не нужен» (дилеру: «Звонок по проекту не понадобится, ответ придёт сюда»). Подтверждение сохранять (calls_confirmed в Airtable); SYS-06/SYS-07 — только подтверждённые, «напомню за час» сделать реальным; напоминания о звонках Лолы — Лоле.

**Р8. Два звонка в анкете (15 и 30 минут) — оставить оба.** В вопросе указать, с кем звонок и зачем: «Звонок с Егором на 15 минут — познакомиться с проектом. Когда удобно?» / «Звонок на 30 минут перед регистрацией…» (имя — по маршруту). Добавить кнопку «← Другой день» (ENG-08).

**Р9. Кнопку «Продлить» не добавлять.** SYS-05: убрать «продли или откати» → «Истёк срок статуса. Откати или оставь как есть:»; кнопки по строке «↩️ Откатить {проект · менеджер}» + общая «Оставить как есть». Дата — дд.мм.гггг. Дилеру по истёкшему сроку еженедельное напоминание (REM-02) не слать после даты истечения больше одного раза.

**Р10. Список истёкших сроков — каждый день, пока не решено.** Оставить ежедневно; по дилерам Лолы — Лоле (см. Р12).

**Р11. Подключение нового человека — как сейчас** (через Claude). Только тексты: ADMM-01 без Telegram ID («Новый человек в боте: {имя}, @{username}. Чтобы подключить — попроси Claude внести его и назови компанию»). SYS-03: по истечении 7 дней написать и самому человеку: «Не получилось подключить тебя к программе. Если вопрос актуален — напиши Егору напрямую.» (обещание DLR-02 не должно висеть).

**Р12. Лола получает по своим дилерам:** утреннюю сводку (SYS-14 / ALR-02 — её часть), истёкшие сроки (SYS-05), напоминания о звонках (SYS-06/07), заявки > 48 ч (SYS-13), новых людей — нет (Р11 остаётся у Егора), ошибки — только касающиеся её заявок, по правилу 1.9.

**Р13. Рассылка о чужой предрегистрации (DLR-37) — оставить, но показывать.** В копии «Взято в работу» строка: «Разослано другим дилерам на объекте: {имена}». Текст дилерам по правилу 1: «На объекте {Название} другой партнёр получил предрегистрацию. Чтобы сохранить приоритет — дополни данные или запроси предрегистрацию.» + «Открыть проект».

**Р14. «Пока не знаю» в анкете (ENG-02, вопросы фазы 2–3).** Кнопка «Пока не знаю — отправить без этого» не прерывает анкету, а пропускает только этот вопрос (как в project_fill). Подпись: «Пока не знаю — пропустить». Если из-за пропусков заявка уходит этапом ниже — сказать это в итоговой сводке (ENG-17): «Подаётся как предрегистрация: для регистрации не хватает — {…}».

**Р15. Регистрацию не предлагать без подтверждённого контакта (ENG-14).** Гейт «Есть квотация? Тогда можно подать на регистрацию» показывать только если Contact Level подтверждён (переписка/контакт с клиентом, встреча). Иначе в сводке: «Для регистрации нужен подтверждённый контакт с клиентом — добавишь позже через «Дополнить материалы»».

**Р16. Проекты до 30 000 € — «регистрация по упрощённой схеме».** Привести CRD-05 и DLR-30 к этой формулировке: убрать «предрегистрация и регистрация не предусмотрены» → «Для проектов до 30 000 € по прайсу действует регистрация по упрощённой схеме: защита — номер квотации на срок её действия. Квотацию запрашивай в бэк-офисе, Егор в копии.» CRD-05: «обнови объём через «Обновить проект»» — указать реальный путь («Сообщить новость»), раз отдельного пункта нет. DLR-33: выводить срок действия квотации датой.

## 3. Петли и тупики у дилера (согласовано отдельно)

1. **ENG-25 (VAGUE_HINT).** На каждом обязательном вопросе — кнопка «Пока не знаю» (в фазе 1 — пропускает вопрос, в сводке «не указано»). Отклонять как пустой только короткий ответ до трёх слов из стоп-списка («не знаю», «пока нет», «неизвестно»…). Не отклонять ответы, где после «нет/пока» есть содержание («Нет изменений, клиент выбрал…», «Сбербанк, филиал уточняется»), и законный ответ «нет» в info_reply. Новый текст: «Напиши, что известно. Если пока ничего — нажми «Пока не знаю».»
2. **ENG-11 / ENG-23 (подтверждение контакта).** Добавить кнопки «Пришлю позже» (уровень записывается с пометкой «без подтверждения») и «← Назад к выбору». На варианте «Готов к встрече с клиентом вместе с Andreu World» файл не просить.
3. **Contact Level — варианты.** Убрать «Документы от бюро» (решение Егора: документы бюро не подтверждают контакт с клиентом; документы бюро собираются в вопросе о материалах). Под «Переписка или прямой контакт с клиентом» подсказка: «Например, письмо клиента о закупке». Развести два почти одинаковых выхода: «Контакт есть, подтвердить пока нечем» (Declared) и «Контакта с клиентом пока нет». Обновить подсказку вопроса и CONTACT_RU (убрать «документы от бюро»).
4. **Номер квотации (project_quote, Simplified Quote №).** Кнопка «Номера пока нет» → возврат к карточке проекта / к гейту без потери ответов. На упрощённом гейте убрать ложное «Сначала дополним…» (ENG-12). Подсказка к ENG-15: куда отправить запрос квотации.
5. **Бюро в новой заявке (Specifier, AW Origin, Lead Architect).** Добавить «Бюро ещё не выбрано» (как в project_fill). Подсказку ENG-32 — по реальной подписи кнопки. ENG-33 «вернись к вопросу о бюро» → кнопка «Архитектор пока неизвестен». На AW Origin — «Пока не знаю». При частном архитекторе кнопка «Да, заложен архитектором». «ГАП» → «главный архитектор проекта».
6. **Пропадающий пропуск.** Вернуть кнопку пропуска после «Да» на гейте 1 (engine._no_skip) и в режиме исправления (ENG-37, _can_stop). В prefill необязательные вопросы (адрес, площадь) — с «Пропустить».
7. **DLR-20 / CRD-03.** next_step_body вызывать с реальным дилером: предрегистрированному писать «Для перехода на регистрацию».
8. **Устаревший текст про бюро** (CRD-04, DLR-20, REM-03, ADM-09): «🤝 Подтверждение контакта с клиентом — сейчас «{уровень}». Нужна переписка с клиентом или его контакт.» Предупреждение в ADM-09 про Declared — по текущему правилу: для предрегистрации контакт не нужен, для регистрации нужен подтверждённый.
9. **Прочие тупики:** ENG-19 — «← К сводке», предупреждать, что при исправлении вопроса с файлами старые файлы удалятся; ENG-40/ENG-09 — не повторять экран молча, а сказать «Выбери вариант кнопкой»; ENG-10/ENG-24 detail — «← Назад»; DLR-04 — файл вне диалога не выбрасывать молча: «Файл получил. К какому проекту он относится?» + список проектов (→ дополнение) или «Выбери действие внизу»; DLR-19, DLR-12, SYS-11 «Продолжить» при сброшенном состоянии — сообщение «Эта заявка уже закрыта» + меню; ERR-01 — «Что-то пошло не так. Нажми /cancel и начни заново — ответы этого диалога не сохранились» (или сохранились — по факту) + меню; DLR-03 — перед закрытием незаконченной анкеты спросить «Закрыть «…» без отправки?» Да/Нет.
10. **Анкета, мелкое:** ENG-13 — число вопросов считать, а не зашивать; ENG-39 — «последний вопрос» с учётом гейтов; Materials — убрать «квотация Andreu World» из списка (её спрашивают отдельно); Bureau Documents — задавать до звонка; Order Month Final — кнопка «Не изменился»; Quotation / Proforma № в фазе 3 — без «Пока не знаю» (дилер только что сказал, что квотация есть), с подсказкой формата; check_address — не ловить «но» внутри слов, лимит 120 символов; ENG-06 «Уже 1 файл»; ENG-04/PHR-08 — для страны «Другая» писать «время по Валенсии (Испания)».

## 4. Проверяющий: тексты и кнопки

- **ADM-09 / ADMM-03 / SYS-13** — по правилу 1.5. Заголовок «💬 Ответ на твой запрос» → «💬 {Имя} ответил на твой запрос по {проект}: «{твой запрос}»». Если не загрузились файлы — показать проверяющему (сейчас знает только дилер, DLR-27). Analysis дублей — по-русски, причины совпадения видны целиком (не обрезать до 40 знаков; переносить в текст сообщения, на кнопке — название и референс).
- **ADM-30 / ADM-31** — показывать, что произойдёт: «Принимаем «{проект}» как {этап}. Дилеру уйдёт: «…». Напиши комментарий или отправь без него.» Если тип заявки меняется на пошаговую — сказать об этом.
- **ADM-34, ADM-48, ADM-14** — в кнопках референс; ADM-48 — с названием заявки и кнопкой «Отмена» (откатывающей записанный отказ).
- **ADM-35, ADM-37, ADM-39** — кнопка «Отмена»; образец формата названия; без слова «Projects».
- **ADM-33, ADM-28, ADMM-02** — не «нажми решение ещё раз», а прислать карточку заново с кнопками.
- **ADM-15 «Отменено»** — что отменено и в каком состоянии заявка.
- **ADM-19** — разные тексты для «Пока оставить» (Р1) и для «Отмена» в меню отката.
- **ADM-20, ADM-21, ADM-22, ADM-05** — имя менеджера и его текущий статус в тексте; без «?» и rec… вместо имени; если повышать некуда — сказать почему и оставить только «Откатить» / «Отмена».
- **ADMM-11 / CRD-13** — русские строки вместо «Simplified → Full», «People»; при ответе на запрос информации — подтверждение и проверяющему, и дилеру (сейчас тишина); ADMM-12 — повторять причину/комментарий, ушедшие дилеру.
- **SYS-08** — имя менеджера в тексте.
- **SYS-02, SYS-03** — без «People», «запись».
- **CMD-12, CMD-15, ADM-11** — без «People», «Username», «Inbox»; CMD-15 — пример без реального человека, кнопка «Отмена»; CMD-11 — если проверяющего нет в базе, сказать об этом; CMD-16 — «Ждём ответа дилера» без «Need more info», список людей с разбиением.
- **SYS-14 / ALR-02** — «Застряли решения: {N}» → список с кнопкой «Показать» (открывает карточки по Р5). Строку «Новые люди ждут добавления» — понятным текстом.
- **ALR-01 / ERR-02** — по правилу 1.9. Одинаковая повторяющаяся ошибка не пропадает: раз в час — «Ошибка повторяется: …, {N} раз за час».
- **ADM-12** (мёртвый код), **ENG-20**, **CRD-10 вторая ветка** — удалить.

## 5. Дилер: тексты

- **DLR-27 / PHR-07** — единый голос: «Получил информацию по проекту. Ответ — в течение 72 часов, придёт сюда.»; новость — «Записал новость, передал {Егору|Лоле}.»; без двойного «передал Егору».
- **DLR-30 / CRD-01** — «статус уведомление» → «уведомление о плейсменте»; не слать «Заявка принята», если статус выставлен вручную без заявки — заголовок «Статус по проекту изменён». CRD-02 «Других статусов на объекте нет» → «Других партнёров на объекте нет».
- **CRD-04** — термины как в анкете: «материалы», «альтернативы Andreu World», «заявлено ли у других производителей».
- **CRD-12** — что именно внесли и что осталось до следующего этапа.
- **DLR-36** — с project_line; кнопка «Ответить».
- **DLR-38** — реальное название кнопки «Дополнить материалы»; уходит всем людям компании, как DLR-30.
- **CMD-04, CMD-06** — упомянуть регистрацию и «Запросить предрегистрацию / регистрацию» в «Обновить проект». CMD-05 — указать, по какому времени (страна из базы). CMD-08 — если отменять нечего: «Отменять нечего».
- **REM-01** «по твоим плейсментам»; REM-03 без тавтологии и без «бюро» на стадии «Выбор архитектора»; REM-04 «последняя новость — дд.мм.гггг».
- **ENG-35, DLR-24** — что дальше: «Новых материалов нет — ничего не отправил. Можно запросить следующий этап или сообщить новость.» + кнопки.
- **DLR-08** — не расшифровывать голосовые незнакомых пользователей.
- **PHR-01…PHR-04** — испанские реплики («Ола», «Перфекто», «Грасиас») оставить, но не после пропуска; убрать двусмысленное «Есть.».

## 6. Как сдавать работу

1. Делать в отдельной ветке. Код, тексты и логику — по этому документу; Airtable-схему не менять без отдельного согласования (кроме записи Won/Lost и подтверждения звонка, Р6, Р7).
2. После правок сгенерировать `docs/messages_after.md` — та же таблица, что в описи, с колонками «было» / «стало» для каждого изменённого ID, и список ID, которые удалены.
3. Добавить админ-команду `/preview {сценарий}`: бот присылает проверяющему все сообщения сценария с тестовыми данными — карточки проверяющего и сообщения дилеру — ровно как они будут выглядеть. Сценарии: new, upgrade, fill, news, quote, won, lost, call, expiry, rollback, unknown, errors, digest.
4. Не деплоить в прод, пока Егор не посмотрит `/preview` по всем сценариям.
